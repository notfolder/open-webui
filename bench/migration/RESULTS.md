# 計測結果（2026-11-14〜15）

PostgreSQL 15.20（`postgres:15`）、Mac mini 上の OrbStack（データは外付け SSD）、コンテナのメモリ 12 GB。
ダミーデータは実物の 0.7.2 の行に合わせた形式（日本語 8・英語 2 の自然な文章、チャット 1 件は平均 19 メッセージ・保存後 約 62 KB）。
PostgreSQL の設定: shared_buffers=3GB, max_wal_size=16GB, checkpoint_timeout=30min, maintenance_work_mem=1GB（ほかは既定）。

## 大きさ（100 万件、最終版、移行後）

- chat: 62 GB（移行前から）/ chat_message: 38.6 GB（うちインデックス 9 本 6.25 GB、主キー 1.92 GB）/ DB 全体: 101 GB
- メッセージ 1,909 万件。移行後の DB ≒ chat テーブル × 1.66

## 式（最終版、この Mac での時間）

    S   = pg_total_relation_size('chat') を GB にした値
    N   = 共有チャットの行数（chat.user_id が 'shared-' で始まる行）
    RAM = PostgreSQL のコンテナが使えるメモリ（GB）
    r   = RAM / (1.66 × S)            … 0.05〜1.2 の範囲に丸める

    時間（秒） = S × (70 − 17.5 × ln r) + N × (r ≥ 1 なら 0.03、そうでなければ 0.11)

実測 3 点との誤差は 5% 以内、メモリを絞った 4 点とは 12% 以内。同じ条件でも 10〜15% ぶれる。
前提: メッセージ 1 件あたりの chat テーブル上の大きさが約 3.2 KB（S ÷ メッセージ数）。これより小さい（短いメッセージが多い）と、
インデックス作成の比重（100 万件で全体の約 35%）が増える。

## 効かなかったもの

wal_buffers（16 MB〜256 MB）、maintenance_work_mem（64 MB〜2 GB、10 万件）、wal_level=minimal、default_toast_compression=lz4、
JSON の展開を SQL に置き換える（4〜20 倍遅い。`perf/migration-sql-backfill-experiment`）。PostgreSQL 15 と 16 の差もなかった。
